# Observability

What you can see about a running system, where it comes from, and how to reach it.
The same stack runs on the local cluster and in production; only sizing and storage
change.

| Signal | Produced by | Shipped by | Stored in | Seen in |
|---|---|---|---|---|
| Metrics | every service on `/metrics` (Prometheus text), Envoy on its admin port | VictoriaMetrics scrapes pods annotated `prometheus.io/scrape` | VictoriaMetrics, 30 d | Grafana dashboards, PromQL |
| Traces | every service (OTLP/gRPC), Envoy as the root span | OpenTelemetry Collector gateway → Tempo | Tempo, local blocks | Grafana Explore, TraceQL, service graph |
| Logs | every service as JSON on stdout with `trace_id`, Envoy access logs as JSON | OpenTelemetry Collector agent tails pod logs, parses the JSON, adds k8s metadata | VictoriaLogs, 30 d | Grafana Explore, LogsQL |
| Span metrics, service graph | Tempo's metrics-generator from traces | remote-write | VictoriaMetrics | Traces dashboard, node graph |

Why these: VictoriaLogs indexes every field, so `trace_id:="…"` is a direct lookup and
full-text search works without a label selector; it and VictoriaMetrics are Apache-2.0,
run as one binary each and cluster later. Tempo is the best-integrated trace store for
Grafana. The upstream OpenTelemetry Collector keeps the pipeline backend-neutral.
Research notes with sources are in the session that chose them; the short version is in
[docs/README.md](README.md).

## Reaching it locally

```sh
mise run local:up        # k3d cluster, once
mise run local:build     # images into the cluster
mise run local:deploy    # observability + envoy + services, waits for readiness
mise run local:traffic   # 30 rounds of validate through Envoy so there is data
mise run k9s             # the cluster in a TUI
```

| URL | What |
|---|---|
| http://localhost:3000 | Grafana, `admin` / `admin`, anonymous viewers allowed. Dashboards tagged `tbd`. |
| http://localhost:9090 | VictoriaMetrics UI: PromQL, targets, series |
| http://localhost:18080 | Envoy edge: REST, SSE, GraphQL, WebSocket, gRPC |
| http://localhost:15051 | Envoy engine load balancer, gRPC |
| http://localhost:14317 | OTLP/gRPC into the collector, for processes running on the host |

Or through Ansible, same result: `mise run ansible:local`.

## Dashboards

Sources live in `devops/grafana/dashboards/*.json` and reach Grafana as a ConfigMap
generated by kustomize. Edit a JSON file and run `mise run grafana:reload`; Grafana rolls
and the change is live in a few seconds. Dashboards are provisioned read-only. To design
in the UI, edit a copy, then Share → Export with "export for sharing externally" off, and
paste the JSON back into the file.

| Dashboard | Shows |
|---|---|
| tbd / Overview | RPS, error rate, p50/p99 and in-flight by service; active streams; engine-client calls from the protocol; injected faults; CPU and memory; recent logs |
| tbd / Engine | per-RPC rate, errors and latency, latency heatmap, streams by kind, stream items/s, faults, logs |
| tbd / Protocol | per-route rate by transport, status codes, latency, WebSocket and SSE gauges, engine-client latency and errors, logs |
| tbd / Envoy | edge and engine-LB request rates and codes, upstream health and retries, outlier ejections, access logs |
| tbd / Traces | TraceQL search, service graph from span metrics, span-metrics rates |

Datasource UIDs, for hand-written panels: `victoriametrics`, `victorialogs`, `tempo`.

## Following one request

1. Every request gets a `trace_id`. Envoy starts the trace and propagates W3C
   `traceparent`; the protocol adopts it and forwards it to the engine; a client can also
   supply its own `traceparent` and it is honoured.
2. In Grafana Explore with the Tempo datasource, search `{ resource.service.name = "protocol" }`
   or paste a trace id. The trace shows Envoy → protocol → engine spans with the route and
   RPC names.
3. From any span, "Logs for this span" opens VictoriaLogs filtered by that `trace_id`.
   From a log line, the `trace_id` field links back to the trace.
4. In VictoriaLogs directly: `trace_id:="<id>"` returns every line from every service and
   Envoy for that request. `service.name:engine level:ERROR _time:1h` is a typical hunt.

## What the services record

Names are constants in `crates/common/src/metrics.rs`; every metric carries a `service`
label set once per process.

| Metric | Type | Labels | Meaning |
|---|---|---|---|
| `tbd_requests_total` | counter | transport, route, status | requests handled |
| `tbd_request_duration_seconds` | histogram | transport, route | time to answer, or to first response on streams |
| `tbd_requests_in_flight` | gauge | transport | requests being handled now |
| `tbd_streams_active` | gauge | kind | open streams: `subscribe`, `session`, `ws`, `sse` |
| `tbd_stream_items_total` | counter | kind, direction | items on streams |
| `tbd_engine_client_requests_total` | counter | route, status | protocol → engine calls |
| `tbd_engine_client_duration_seconds` | histogram | route | protocol → engine latency |
| `tbd_faults_injected_total` | counter | kind | faults the chaos handle injected |
| `tbd_build_info` | gauge | version | always 1 |
| `process_*` | various | | CPU, RSS, fds, threads, from `metrics-process` |

Histogram buckets run from 0.5 ms to 30 s so a hung backend is visible, not clipped.

Spans: `http.request` (route, method) and `grpc.request` (rpc.method) on the protocol,
`grpc.request` on the engine, `envoy ingress` at the edge. Logs are JSON with
`timestamp`, `level`, `message`, `target`, and the enclosing span's fields including
`trace_id`.

## Configuration

| Env | Default | Meaning |
|---|---|---|
| `ENGINE_METRICS_ADDR` / `PROTOCOL_METRICS_ADDR` | `0.0.0.0:9464` / `:9465` | Prometheus listener; unset disables |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | unset | OTLP/gRPC collector; unset means trace ids are generated but nothing is exported |
| `OTEL_SERVICE_NAME` | binary name | `service.name` on spans |
| `OTEL_TRACES_SAMPLER_ARG` | `1.0` | root sampling ratio; lower it under real load |
| `LOG_FORMAT` | `text` | `json` in containers |
| `RUST_LOG` | `info` | filter; per-request lines are at `debug` |

## Production notes

- Sampling: keep `1.0` until traffic makes Tempo's storage the bottleneck, then sample at
  the root and keep error traces with a tail-sampling processor in the collector gateway.
- VictoriaLogs and VictoriaMetrics shard in cluster mode but do not replicate; run two
  independent copies fed by the collector, and snapshot the PVCs. Object storage for
  VictoriaLogs is on the vendor's roadmap, not shipped.
- Tempo in production runs in microservices mode with Kafka and object storage; the
  monolithic config here is for one node.
- Envoy's per-request access logs are the highest-volume log source. Keep them; they are
  what answers "was the request even received", but budget the storage.

## Troubleshooting

| Symptom | Look at |
|---|---|
| A service pod is Running but not Ready | `kubectl -n tbd logs deploy/protocol`: readiness fails when the engine is unreachable through Envoy |
| No traces | `OTEL_EXPORTER_OTLP_ENDPOINT` in the ConfigMap, then `kubectl -n observability logs deploy/otel-collector` |
| No logs from a pod | `kubectl -n observability logs ds/otel-agent`; the agent excludes its own logs and needs `/var/log/pods` on the node |
| No metrics for a pod | it needs the `prometheus.io/scrape`, `port` and `path` annotations; VictoriaMetrics' targets page at :9090 lists what it sees |
| Envoy returns 503 | `kubectl -n tbd exec deploy/envoy -- envoy --version` to confirm, then the admin `clusters` endpoint through a port-forward: hosts marked unhealthy failed the active health check |
| Dashboards changed but Grafana shows old ones | `mise run grafana:reload`; the ConfigMap name carries a content hash, so a re-apply rolls the pod |
